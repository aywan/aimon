# База знаний: нетривиальные решения прошивки

Этот файл — накопительная база решений, которые **нельзя вывести просто чтением
кода**: они основаны на эмпирике, обходах багов вендора/железа/библиотек, или
неочевидных архитектурных договорённостях. Цель — не дать наступить на те же
грабли дважды.

## Как пополнять

Добавляя запись, пиши не "что делает код" (это видно из кода), а:
- **Что** — сама договорённость/решение.
- **Почему** — какая скрытая причина/баг/ограничение за этим стоит.
- **Чем грозит** — что сломается, если поменять это не зная контекста.
- Ссылка `файл:строка` на место в коде.

Держи записи короткими. Если решение перестало быть актуальным (код изменился) —
правь или удаляй запись, а не оставляй устаревшей.

## main.c

- **`ble_app_init()` сразу после `lcd_init()`, до `render_init()`/`mic_init()`.**
  (`main/main.c`) Почему: BT-контроллер ESP32-S3 выделяет буферы **только из
  внутренней DRAM**, PSRAM ему недоступен. LVGL (double framebuffer) и I2S
  микрофона съедают этот heap; если NimBLE поднять позже —
  `nimble_port_init()` возвращает `ESP_ERR_NO_MEM` (лог `BLE_INIT: Malloc
  failed`), `ESP_ERROR_CHECK` зовёт `abort()`, плата уходит в reboot-loop.
  `lcd_init()` всё равно первый: без EXIO PWR_HOLD питание отвалится, пока
  палец на кнопке. `rtc_clock_init()` — после BLE, до `render_init()`: I2C, не DRAM,
  но первый кадр главного экрана должен уже уметь прочитать сохранённое время.
  Чем грозит: вернуть BLE «после UI, чтобы успел
  подписаться render» — снова цикл перезагрузок. `ble_paired` из host-sync
  подхватывается повторным `update_settings_widgets()` после
  `state_set_on_change_cb()` в `render_init()`.
- **QSPI: `psram_dma_direct` + `pclk_hz=10 MHz`, не 40.** (`lcd.c`) Почему:
  BT-контроллер съедает DMA-DRAM (даже с `SPIRAM_MALLOC_RESERVE_INTERNAL=96K`
  bounce всё равно падает: `Failed to allocate priv TX buffer`). DMA из PSRAM
  на 40 МГц даёт `DMA TX underflow` — белый экран, жёлтые полосы, LVGL
  зависает в `wait_for_flushing`, тач не отвечает. 10 МГц — эмпирика, чтобы
  octal PSRAM успевал кормить 4 линии. Чем грозит: вернуть 40 МГц «как у
  вендора» при включённом BLE — снова полосы; убрать `psram_dma_direct` —
  снова нет DRAM на bounce.

## battery

- **Формула ADC→напряжение взята из вендорского примера Waveshare** (`battery.c:10-13`),
  не выведена из документированного делителя по схеме этой платы. Меняя
  `BAT_DIVIDER_RATIO`, сверяйся с вендорским `adc_bsp.c`, а не только со схемой.
- **`BAT_VOLTAGE_PRESENT_MIN = 2.0f` не проверен на реальном железе** —
  явно помечено как TODO (`battery.c:25-29`, `state.h:33-35`). Не полагайся на
  корректность различения "нет батареи" / "батарея разряжена" без проверки.
- **`poll_cb(NULL)` вызывается синхронно сразу после старта таймера** (`battery.c:100`),
  чтобы не ждать первого тика — иначе UI 5с после загрузки не показывает данные
  о батарее.
- **`read_voltage()` при ошибке ADC/калибровки молча возвращает `0.0f`** (`battery.c:38-49`),
  что неотличимо от "батарея не подключена" (т.к. ниже `BAT_VOLTAGE_PRESENT_MIN`).
  Кратковременный глюк ADC/I2C покажет в UI "нет батареи", а не ошибку/stale-состояние.

## ble

- **Новое спаривание только по кнопке Pair на Settings, не 60с от boot.**
  (`ble.c` `ble_app_begin_pairing()`, `BLE_APP_PAIRING_WINDOW_SEC`).
  Почему: окно с boot оставляло плату open-pairing любому central рядом.
  Passkey генерируется в момент нажатия и показывается сразу; в
  `BLE_GAP_EVENT_PASSKEY_ACTION` инжектится тот же PIN, а не новый random —
  иначе цифра на экране не совпадёт с тем, что ждёт хост. Чем грозит:
  вернуть boot-окно или генерировать PIN только в PASSKEY_ACTION — UI и
  клиентский README снова разъедутся, а Pair «покажет PIN», которого стек
  ещё не знает.
- **`conn_maybe_bonded_rpa()` нужен из-за macOS RPA** (`ble.c`): при
  переподключении Mac использует resolvable private address, который на момент
  `CONNECT` ещё может быть не resolved. Без этой проверки уже забондженный Mac
  будет отвергнут как неизвестный пир.
- **Security initiation запускается только когда identity уже известна**
  (`ble.c`) — либо bonded, либо похоже на bonded RPA, либо открыто окно после
  Pair (`BLE_APP_PAIRING_WINDOW_SEC`). Запуск security "вслепую" стартует
  новое спаривание вместо LTK-шифрования, что macOS откажется принимать.
- **`BLE_GAP_EVENT_REPEAT_PAIRING` стирает бонд только при открытом окне Pair.**
  (`ble.c`) Почему: пример bleprph всегда делает `delete_peer` + `RETRY` — там
  устройство всегда pairable. У нас после ребута окно закрыто; macOS при
  реконнекте по RPA часто шлёт Pairing Request, если LTK-шифрование не
  успело за resolution identity. `RETRY` стирал NVS-бонд, затем
  `PASSKEY_ACTION` отклонял новое спаривание — «пейринг не переживает
  перезагрузку». Без окна — `IGNORE`, LTK остаётся. Чем грозит: вернуть
  безусловный `RETRY` «как в примере Espressif» — снова потеря бонда после
  ребута.
- **Не рвать линк на `ENC_CHANGE` fail, пока пир bonded или RPA при живом бонде.**
  (`ble.c`) Почему: Mac шифрует LTK сразу, часто ещё до `IDENTITY_RESOLVED`.
  Поиск ключа по нерезолвленному RPA даёт fail; terminate в этот момент
  гоняет реконнект по кругу и выглядит как потерянный пейринг. Security
  повторно стартует из `IDENTITY_RESOLVED`. Чем грозит: вернуть «любой
  enc fail + закрытое окно → drop» — забондженный Mac после ребута снова
  не подключится.
- **Forget на плате не забывает LTK на macOS.** `ble_app_forget_paired()`
  только `ble_store_util_delete_peer()` + разрыв линка (`ble.c`). Чем грозит:
  Mac со старым бондом не переспарится сам — нужно Forget и в System Settings
  (то же ограничение, что у `make erase-nvs`).
- **`ble_paired` выставляется из ble, не угадывается UI.** Host-sync читает
  NVS-бонды и зовёт `state_set_ble_paired()`; после нового бонда / Forget —
  то же. Render только читает флаг. Чем грозит: выставить флаг в `ble_app_init()`
  до sync — всегда `false`, кнопка Pair на уже спаренной плате.
- **Passkey живёт в state, BLE не зависит от render.** Иначе
  events→ble→render→events (Pair/Forget идут через `events_post()`).
  Видимость PIN отделена от числа: сгенерированный код может быть `000000`.
  Чем грозит: вернуть `render_show_passkey()` из ble — циклическая зависимость
  CMake; хранить «нет PIN» как `passkey==0` — спрячет легитимный нулевой PIN.
- **75-секундный "silence watchdog"** (`ble.c` `NOTIFY_STALE_MS`,
  `state_set_ble_data_stale()`). Чисто UX: тусклый красный кружок в левом
  верхнем углу главного экрана, **не** разрыв соединения/security. Порог 75с,
  а не 60: клиентский `Flush` может пропускать запись до минуты, если слоты
  не менялись (`timeResyncInterval`), unix всё равно уходит раз в минуту.
  Считаются только GATT control writes, не connect/encrypt — живой линк с
  молчащим клиентом тоже stale. Флаг в `state`, не hook из render: watchdog
  крутится в esp_timer, LVGL трогает только render. Чем грозит: вернуть 70с
  или считать encryption activity — ложные срабатывания относительно
  минутного heartbeat; звать LVGL из watchdog — рейс с LVGL-таском.
- **GAP-имя `aw_extramon_1`, complete local name в primary advertising, не в
  scan response** (`ble.h` `BLE_APP_DEVICE_NAME`, `ble.c` `ble_app_advertise()`).
  Почему: 128-bit UUID + имя не влезают в 31 байт legacy ADV. Имя только в
  scan response даёт пустой `LocalName()` у CoreBluetooth и «Unknown» в
  сканерах, которые не делают scan request — устройство «есть в эфире», но
  не видно в списках и не находится клиентом по имени. UUID уходит в scan
  response. Чем грозит: вернуть UUID в primary / имя в response — снова
  невидимая периферия; удлинить имя так, что оно не влезет вместе с flags.
- **`CONFIG_BT_NIMBLE_NVS_PERSIST=y` обязателен** (`sdkconfig.defaults:31-33`):
  без него ключи бондинга живут только в RAM. После ребута платы macOS всё ещё
  хранит старый LTK и не станет сама переспариваться — переподключение сломается
  полностью, это не просто "приятная опция".
- **`make erase-nvs` стирает бонды, `make app-flash` — намеренно нет**
  (`Makefile:157-158,146-147`). Помни: macOS также нужно отдельно "забыть"
  устройство — у неё свой LTK.

### gatt_svc.c — важный сквозной момент

- **`handle_json_command()` применяет merge-patch слотов главного экрана**
  (`gatt_svc.c`). Ключи `slot_1`…`slot_4`; объект мержится в текущий слот,
  `null` или `"type":"empty"` очищает. `value` clamp 0–100. `fg`/`bg` внутри
  слота — `#RRGGBB` (ровно 6 hex-цифр): `fg` это цвет индикатора дуги у
  gauge **и** цвет тела у text; `bg` — дорожка дуги (на text не влияет).
  Опущенные оставляют предыдущие; unset → дефолты `#3ecf8e` / `#333333`
  (дуга) и белый текст. Топ-уровневый `bg` (старый фон экрана) по-прежнему
  игнорируется — цвет живёт только в `slot_N.fg`/`slot_N.bg`. Неизвестные
  ключи (`top_color`, `led`, …) игнорируются. Диспатч —
  `state_set_slots()`, не LVGL и не `events_post()`: `events` уже зависит от
  `ble` (Pair/Forget), обратная зависимость собрала бы цикл CMake.
  Чем грозит: звать LVGL из GATT callback — рейс с LVGL-таском; тащить
  payload через `events_post()` — либо раздувать enum, либо цикл зависимостей.
  Путать экранный `bg` и `slot_N.bg` — покрасить не тот объект или «цвет не
  применяется», хотя JSON «как раньше».
- **`unix` + `tz_offset` — метка времени с компьютера, не слот.** (`gatt_svc.c`)
  `unix` — UTC-секунды; `tz_offset` — секунды к востоку от UTC (`time.Now().Zone()`
  на macOS). Вместе дают civil time в ЧП компьютера, это то, что пишется в
  PCF85063. Диспатч — `rtc_clock_set_unix()`, не `state` и не `events_post()`: тик
  часов не должен гонять полный редрей, а `events` не может зависеть от ble.
  Опущенный `unix` не трогает RTC. Чем грозит: положить HH:MM в слот — съест
  одну из четырёх ячеек Codex; звать `settimeofday` из render — рейс с GATT.
- **Протокол слотов — merge, не replace всего экрана.** Опущенный `slot_N`
  не трогает ячейку. Чтобы очистить — `"type":"empty"` или JSON `null`.
  Подписи только латиница: встроенный Montserrat 20 без кириллицы (см.
  «Сборка»). Лимиты строк: label 15 символов + NUL, text 31 + NUL
  (`APP_SLOT_LABEL_MAX` / `APP_SLOT_TEXT_MAX` в `state.h`).
- **Payload проверяется на размер (`MAX_JSON_LEN`=512) до копирования в стековый
  буфер** (`gatt_svc.c`) — переполненные/нулевые записи отклоняются
  с `BLE_ATT_ERR_INVALID_ATTR_VALUE_LEN`, а не обрезаются — защита от stack overrun.
- **UUID'ы в заголовке хранятся в обратном (little-endian) порядке байт**
  (`include/gatt_svc.h:15-21`) — рядом даны human-readable строки для клиента.
  Копипаста байт напрямую вместо использования human-readable формы легко
  переворачивает порядок байт.

## events

- **`events_post()` — единственная точка входа для всех пользовательских действий**
  (`events.c`, `events.h:12-21`), чтобы источник события (тач, кнопка, BLE)
  оставался отделён от логики реакции (мутации state). Это **конвенция**, ничем
  не форсируется в коде — новый источник ввода может по ошибке дёрнуть
  `state_set_*()` напрямую и незаметно сломать архитектуру.

## mic

- **ES7210 I2C-адрес (0x40), I2S-пины (mclk:7, bclk:15, ws:46, din:6, dout:45)
  и порядок регистровой инициализации не выводятся ни из схемы, ни из
  `lcd.c`** (`mic.c:10-90`) — найдены только в официальном репо
  `waveshareteam/ESP32-S3-Touch-LCD-3.49`, `Examples/Arduino/08_Audio_Test/
  src/codec_board/board_cfg.h`, запись `Board: S3_LCD_3_49` — **не** в их же
  `board_cfg.txt` (generic-список esp_codec_dev, там этой платы нет вообще).
  Если этот пример когда-нибудь уберут/переименуют из апстрима — искать по
  сигнатуре `S3_LCD_3_49` в истории репозитория, не по имени файла.
- **`s_es7210_init_seq` в `mic.c` — не полный даташит-дамп, а свёрнутый
  частный случай** вендорского `es7210_open()+es7210_start()+
  es7210_mic_select()` (из `esp_codec_dev`), захардкоженный под MIC1+MIC3
  (реально распаянная пара мик на этой плате — MIC2/4 не задействованы),
  slave I2S, 16 бит, максимальный PGA-gain чипа 37.5dB (сознательно —
  метрике важнее чувствительность, чем headroom). Смена набора микрофонов/битности означает
  пересчёт этой таблицы заново из вендорского драйвера, не точечную правку.
- **`MAINCLK_REG02=0xC1` и `OSR_REG07=0x20` жёстко привязаны к MCLK=256×Fs
  при Fs=48000** (`mic.c`, см. комментарий у `MIC_SAMPLE_RATE_HZ`) — это
  конкретная строка вендорской clock-coefficient таблицы (12.288MHz/48kHz),
  не универсальная константа. Смена `MIC_SAMPLE_RATE_HZ` без пересчёта этих
  двух регистров даёт тишину или мусор на выходе ADC, ошибок при этом не
  будет — I2C/I2S всё равно проинициализируются успешно.
- **ES7210 сконфигурирован как I2S slave** (`mic.c`, `es7210_update_bits(...,
  0x08, 0x01, 0x00)`) — ESP32 сам генерирует MCLK/BCLK/WS
  (`I2S_ROLE_MASTER` в `mic_i2s_init()`). Это соответствует тому, как
  вендорский `codec_init.c` инициализирует ES7210 (`master_mode` не
  выставлен → false по умолчанию) — смена роли без синхронной правки I2S
  конфига разорвёт тактирование.
- **Системная I2C-шина (I2C0, GPIO47/48) шарится с TCA9554-экспандером
  из `lcd.c`, а не поднимается заново** (`lcd.h`: поле `sys_i2c_bus` в
  `lcd_handle_t`, `lcd.c: expander_init_and_reset()`) — второй вызов
  `i2c_new_master_bus()` на тех же пинах не пройдёт, драйвер `i2c_master`
  этого не позволяет. Любой новый потребитель этой шины должен получать
  handle через `lcd_handle_t`, не создавать свою шину.
- **`mic_get_noise_level()` — не через `state.c`, сознательно в обход
  общего notify-редрея** (`mic.c`, комментарий над `mic_task()`) — обновляется
  много раз в секунду по мере прихода I2S-чанков, а `state_set_*()` дёрнул бы
  полный редрей всего экрана статуса на каждое значение. `render.c` сам
  опрашивает геттер отдельным быстрым `lv_timer` (200мс), а не подписывается
  на изменения state.
- **Уровень шума — грубая эвристика, не калиброванный dB(SPL)**
  (`mic.h`, `NOISE_RMS_FULL_SCALE` в `mic.c`) — RMS по 16-битным сэмплам,
  делённый на неоткалиброванный делитель 4000. Годится для "тут громко/тихо"
  на графике, не для реальных измерений.

## rtc

- **Адрес 0x51 и регистровая карта PCF85063 — из вендорского примера, не из
  схемы** (`rtc.c`, Waveshare `02_I2C_PCF85063` / `RTC_PCF85063_ADDR` +
  SensorLib `SensorPCF85063`). Шину не поднимаем заново: тот же I2C0, что у
  TCA9554 (`lcd_handle_t.sys_i2c_bus`), как у `mic.c`. Публичные функции
  названы `rtc_clock_*`, не `rtc_init`: в `esp_hw_support` уже есть
  `rtc_init()` периферии ESP32-S3, линкер падает с multiple definition.
  Чем грозит: вторая `i2c_new_master_bus()` на GPIO47/48 не пройдёт;
  «как в даташите другой платы» легко поменять адрес; вернуть имя
  `rtc_init` — снова ошибка линковки.
- **На init нет software reset (0x58 в Control_1).** Почему: сброс обнуляет
  календарь, а смысл чипа — держать время после hard power-off. Только
  24h-режим и сброс STOP, как `SensorPCF85063::initImpl`. OS-флаг в секундах
  (bit 7) = время недостоверно → UI `--:--` до первой BLE-записи. Чем грозит:
  «для чистоты» сбрасывать чип на каждой загрузке — часы снова 00:00 после
  каждого питания.
- **В чип пишется local civil time (unix + tz_offset), системные часы ESP32
  тикают этим же значением как UTC.** (`rtc_clock_set_unix`, `timegm_utc` через
  `TZ=UTC0`) Почему: иначе каждый тик UI ходил бы на I2C, а `localtime()`
  на прошивке не знает ЧП компьютера. `setenv("TZ")` — процесс-глобальный
  побочный эффект; ничего в прошивке не должно звать `localtime()` ожидая
  настоящий UTC. Чем грозит: писать в чип UTC, а показывать без смещения —
  часы не в ЧП компьютера; не выставлять `TZ=UTC0` перед `mktime` — сдвиг
  на дефолтный TZ newlib.
- **Сохранение времени при `lcd_power_off()` не проверялось на железе.**
  Вендор обещает time retention (отдельная VBAT у PCF85063), но hard
  power-off через EXIO PWR_HOLD обесточивает всю плату — жив ли backup-rail,
  неизвестно. Если нет, после включения снова `--:--` до BLE. Не выдавать
  persistence за проверенный факт.
- **CAP_SEL (7 vs 12.5 pF) не трогаем** — SensorLib тоже не выставляет.
  Не сверялось со схемой этой платы.

## sd

- **Пины TF-слота — из вендорского `04_SD_Card`, не из схемы и не с 7".**
  (`sd.c`) 1-bit SDMMC: CLK GPIO41, CMD GPIO39, D0 GPIO40. На 7" у Waveshare
  другой разъём (SPI + CS на экспандере) — копипаста оттуда не заведётся.
  `format_if_mount_failed=false`: отсутствие карты — норма, не формат.
  Чем грозит: SPI-пины 11–13 на этой плате заняты QSPI LCD.
- **Mount только на boot, сразу `sd_unmount()` после чтения.** (`render.c`
  `render_init`) FATFS+SDMMC держат DMA-внутреннюю DRAM, которая уже в
  дефиците из-за BLE. Карта после загрузки не нужна: `full_refresh` всё равно
  рисует из RAM. Смена PNG — только ребутом. Чем грозит: оставить карту
  смонтированной «на всякий случай» — снова давить BLE/LCD DMA.
- **`bg.png`/`fg.png` в корне FAT32, логический кадр 640×172.** После
  `LV_DISPLAY_ROTATION_270`, не native 172×640 панели. Нет файла → bg чёрный,
  fg нет. Не путать с JSON `slot_N.bg`/`fg` (цвета дуги). Mount после BLE на
  этой плате проходит (лог `sd: mounted` при живом NimBLE). Как готовить:
  8-bit sRGB PNG (deflate/сжатие не важно — lodepng разжимает в RGBA);
  `bg.png` непрозрачный (PNG24, flatten на чёрный); `fg.png` — PNG32, альфа
  там, где должны просвечивать слоты. На macOS:
  `sips -z 172 640 --setProperty format png in.png --out bg.png`
  (`-z` это высота×ширина). ImageMagick:
  `magick in.png -resize 640x172! -strip PNG24:bg.png` и `PNG32:fg.png`.
  Портрет 172×640 на этой прошивке будет растянут в ландшафт, не «как на панели».
- **Обои нельзя декодировать через builtin `lv_malloc` 64KB.** (`sdkconfig.defaults`
  `CONFIG_LV_USE_CLIB_MALLOC`) lodepng зовёт `lv_malloc`; кадр 640×172 RGBA
  ≈440KB → ошибка 83 `memory allocation failed`, файлы с карты читаются, UI
  чёрный. clib malloc + `SPIRAM_MALLOC_ALWAYSINTERNAL=16384`: мелкие объекты
  LVGL остаются во внутренней DRAM, большие кадры уходят в PSRAM. Чем грозит:
  вернуть `CONFIG_LV_USE_BUILTIN_MALLOC` — снова пустой фон при живых PNG.

## lcd

- **GPIO21 ("LCD_RST" в примерах V1) на этой V2-плате — на самом деле LCD_TE**
  (неиспользуемый), реальный reset идёт через TCA9554 I/O expander (`lcd.c:16-21`).
  GPIO8 (подписан в схеме V2 как "EXIO_INT") на деле управляет подсветкой —
  подтверждено эмпирически, расхождение со схемой.
- **Голый импульс на GPIO21 никогда не сбрасывал панель на V2** (`lcd.c:133-144`):
  панель "оживала" только после полного power cycle (сбрасывает expander), но не
  после soft/EN reset (expander держит регистры). Объясняет, почему код из старых
  примеров "наполовину работает" — после чистой прошивки с обесточиванием, но не
  после reset из `idf.py monitor`.
- **Power-hold latch (EXIO_BIT_PWR_HOLD) взводится первым делом** в
  `expander_init_and_reset()` (`lcd.c:163-169`) — до этого питание держится только
  физическим нажатием кнопки PWR пользователем; любая задержка рискует потерей
  питания посреди инициализации.
- **BL_EN (подсветка) намеренно включается только после reset/init панели**
  (`lcd.c:141-143`), как в заводской прошивке — иначе видно "мусор" на экране.
- **Touch-контроллер AXS15231B не работает через стандартный `esp_lcd_touch`/
  `esp_lcd_panel_io_i2c`** (NAK на каждой транзакции) — используется голый I2C
  handle + фиксированная "магическая" команда (`lcd.c:184-188`, `s_touch_read_cmd`
  на line 62), сверено с вендорской прошивкой.
- **Не используется полный gamma/power/timing init-набор апстрим-драйвера** —
  только sleep-out (0x11) + display-on (0x29) (`lcd.c:69-72`). Комментарий прямо
  называет больший набор "red herring", за которым кто-то уже гонялся, разбирая
  баг-репорт от другой платы.
- **`full_refresh=true` и `sw_rotate=true` в LVGL — обход багов железа, не
  оптимизация производительности** (`lcd.c:201-209`):
  - `full_refresh`: QSPI draw path теряет команду RASET (row address), частичные
    флаши попадают не в тот Y-офсет.
  - `sw_rotate`: аппаратный `swap_xy` на этом чипе "known-broken", ротация
    делается программно через `lv_display_set_rotation`.
  Выключение любого флага визуально ломает экран.
- **100ms задержка после init подсветки** (`lcd.c:247-250`) нужна потому, что
  soft/EN reset не перезапускает общую 3.3V шину так, как это делает отключение
  USB — шине нужно время устаканиться.
- **`lcd_power_off()` не возвращает управление** (`lcd.h:44-51`) — вся плата
  немедленно теряет питание. Это настоящий hard power-off, не deep sleep; код
  после вызова никогда не выполнится.
- **Пин зависимости `esp_lcd_axs15231b ^2.1`** (`idf_component.yml:3-8` в lcd) —
  вендорская рекомендованная 1.0.1 компилируется только под ESP-IDF <6.0
  (использует старое поле `color_space`, переименованное в `rgb_ele_order` в IDF 6.0).

## power_button

- **Опрос через 20ms `esp_timer`, не GPIO interrupt** (`power_button.c:12-13`,
  `GPIO_INTR_DISABLE` на line 51) — простой и эффективный debounce, но
  по-настоящему короткий глитч короче одного периода опроса может быть пропущен
  (нет edge-interrupt fallback).
- **Long-press триггерится в момент пересечения порога 1.5с** (`power_button.c:32-38`),
  не по отпусканию кнопки, и сразу вызывает `lcd_power_off()` (не возвращается).
  Флаг `s_long_press_fired` существует только чтобы не дать событию сработать
  дважды до того, как питание реально отключится.
- **Полный поведенческий контракт задокументирован в одном месте**
  (`power_button.h:7-14`): короткое нажатие — тоггл подсветки; долгое (≥1.5с) —
  жёсткое отключение питания, требующее физического нажатия кнопки для
  перезапуска `app_main()` с нуля (это не resumable sleep/wake, а эквивалент
  холодной загрузки).

## render

- **`EXTERNAL_LOCK_TIMEOUT_MS=100`** (`render.c:9-14`) — `state_set_*()` (и через
  него `on_state_changed()`/LVGL lock) может вызываться не из LVGL-таска, а,
  например, из esp_timer callback батареи. Таймаут вместо блокировки навсегда
  нужен, чтобы зависший LVGL-таск не подвесил ещё и таймер-таск батареи.
  Увеличение/удаление таймаута рискует застопорить другие таймер-driven подсистемы.
- **Тач в `touch_read_cb` — нативные координаты панели, не logical 640×172.**
  (`render.c`) Почему: `lv_display_set_rotation(270)` уже пересчитывает
  pointer в `indev_pointer_proc()` через `disp->hor_res`/`ver_res` (172×640).
  Старый invert-both в logical-space давал правильное *направление* свайпа
  (жесты живут на дельтах), но hit-test кнопок в центре экрана никогда не
  попадал — точка после двойного поворота оказывалась в полосе ~172 px, а
  Pair сидит на x≈320. Жесты после фикса — TOP/BOTTOM, не LEFT/RIGHT.
  Чем грозит: вернуть invert-both «как в KB раньше» — снова мёртвая Pair.
- **`lvgl_cfg.task_affinity = 1`** (`render.c`) — LVGL намеренно держат
  вне core 0, т.к. NimBLE прибит к core 0 (`CONFIG_BT_NIMBLE_PINNED_TO_CORE_0`).
  Изоляция ядер, чтобы радио/BLE-host не подвешивал рендер и наоборот.
- **Главный экран — 4 flex-слота, не scrollable и не clickable** (`render.c`
  `create_main_screen`). Почему: кликабельный ребёнок съедает pointer, и
  `LV_EVENT_GESTURE` на экране не всплывёт — свайп Status/Settings сломается.
  `GESTURE_BUBBLE` оставлен, `CLICKABLE`/`SCROLLABLE` сняты. Gauge — `lv_arc`
  270° (rotation 135), не `lv_scale`: в 160×172 слоте дуга читается, а шкала
  с делениями на Montserrat 20 не влезает. Чем грозит: вернуть clickable на
  слот/арку — снова мёртвый свайп, как раньше с Pair.
- **Обои `bg.png`/`fg.png` — тот же overlay-контракт, что часы.** (`render.c`
  `create_layer_image`). `IGNORE_LAYOUT` + `FLOATING`, не clickable, gesture
  bubble; иначе свайп снова умрёт. `bg` — первый ребёнок (под слотами),
  `fg` — над слотами, но под часами/stale-LED, чтобы HH:MM не прятался под
  непрозрачным углом PNG. В `lv_image_set_src` передаём сам `lv_draw_buf_t`,
  не копию в `lv_image_dsc_t`: `draw_buf_create` ставит `ALLOCATED`, и LVGL
  тогда кастит src в draw_buf и требует `unaligned_data`/`handlers` — у
  обрезанного dsc они NULL, `set_src` молча выходит, виджет пустой. Декод
  через lodepng, compressed PNG `free`. **lodepng в этом дереве патченый:**
  `lodepng_decode32` возвращает `lv_draw_buf_t*`, пиксели в `.data` как RGBA;
  как в `lv_lodepng.c` `convert_color_depth` нужно свапнуть R↔B, иначе
  трактовка `*out` как сырого RGBA копирует заголовок структуры в кадр —
  на железе это был шум, не «плохо сжатый PNG». Дальше native 16-bit
  (`RGB565` / `RGB565A8`) и C2M `esp_cache_msync` (заливка на CPU0, LVGL на
  CPU1). Пиксели в RAM на всю сессию — `full_refresh` перерисовывает кадр
  целиком. Чем грозит: flex-ребёнок / clickable — слоты поедут или мёртвый
  свайп; кормить LVGL путём `S:bg.png` без unmount — держать SDMMC DMA живым;
  снова завернуть буфер в dsc с флагом ALLOCATED — опять невидимые обои;
  вызвать decode32 «как в апстрим lodepng» и читать байты с `*out` — снова
  снег из пикселей.
- **Часы HH:MM — floating overlay, не пятый flex-слот** (`render.c`
  `create_main_screen`). `IGNORE_LAYOUT` + `FLOATING`, не clickable, gesture
  bubble. Почему: ребёнок в row-flex стал бы пятой колонкой и/или съел бы
  pointer. Тик раз в секунду через свой `lv_timer`, опрос `rtc_clock_get_hms()`
  как у mic — не через `state_set_*()`. Шрифт Montserrat 14 (не дефолтный 20).
  Чем грозит: убрать IGNORE_LAYOUT — слоты поедут; сделать clickable —
  снова мёртвый свайп; гонять часы через state — полный редрей каждую секунду.
- **Иконка батареи в том же overlay, что часы** (`render.c` `s_clock_row`,
  `update_battery_icon`). Справа от HH:MM, FontAwesome `LV_SYMBOL_BATTERY_*`
  из уже включённого Montserrat 14 — отдельный символ-шрифт не нужен.
  Красный (`#ff4a1a`) с `BAT_ICON_WARN_PCT=30`, не с телефонных 20%: на этом
  паке линейная оценка 3.3–4.2 В на практике уже «пора заряжать» при
  показанных 30%. Нет батареи → иконка `HIDDEN`, не «пустая». `LV_SYMBOL_CHARGE`
  не показываем: зарядку по тренду напряжения решили не детектить (шумно и
  медленно для живого UI). Чем грозит: сдвинуть порог к 20% «как у телефонов» —
  предупреждение придёт слишком поздно; сделать row clickable — снова мёртвый
  свайп.
- **Stale-LED — тот же overlay-контракт, что у часов** (`render.c`
  `create_main_screen`). 8px тусклый `#6a1818` кружок TOP_LEFT; `HIDDEN`, пока
  `state_get_ble_data_stale()` ложь. Не clickable, gesture bubble. Чем грозит:
  clickable / flex-ребёнок — снова мёртвый свайп или слоты поедут; читать
  watchdog из render напрямую — зависимость render→ble, которой нет.
- **Метка сборки на экране Status — UTC из CMake, не `__DATE__`/`__TIME__`**
  (`render.c` + `gen_build_info.cmake`, `CMakeLists.txt` компонента render).
  Почему: `__DATE__`/`__TIME__` — локальная таймзона машины, собравшей бинарник,
  и два билдера дали бы разный смысл одной и той же строки. CMake
  `string(TIMESTAMP ... UTC)` даёт однозначный UTC. Заголовок
  `build_info.h` перегенерируется на **каждый** `make build` (custom target
  без зависимостей + `OBJECT_DEPENDS` на `render.c`), а не только при
  reconfigure — иначе повторная прошивка того же дерева сохраняла бы старый
  штамп и метка перестала бы отличать вспышки. Чем грозит: убрав always-rebuild
  target, метка будет врать «когда собрали»; подставив `__TIME__` — ещё и
  таймзону. Раньше на главном экране был `"Hello World! " __TIME__` как
  маркер stale GRAM; его сняли вместе с заглушкой главного экрана — живые
  виджеты и UTC-штамп Status эту роль закрывают.

## state

- **`state_set_on_change_cb()` хранит один callback, не список** (`state.c:15-18`,
  `state.h:19-27`). Повторный вызов молча заменяет предыдущего подписчика без
  ошибки. В комментарии написано, что render — "единственный предполагаемый
  подписчик", но код это никак не форсирует — второй модуль, зарегистрировав
  callback, молча сломает обновления UI без предупреждения.
- **В `state.c` нет мьютекса/critical section для static-переменных модуля**,
  хотя `battery.c` (из своего таймер-callback) и `render` (из LVGL-таска через
  тач/жесты) оба вызывают `state_set_*()` из разных тасков — этот факт явно
  признан в комментарии `render.c:9-11`, но сам `state.c` полагается на
  атомарность простых присваиваний FreeRTOS, а не на явную синхронизацию.
  Слоты — POD-структуры с фиксированными буферами, копируются целиком
  (`state_get_slot` / `state_set_slots`); гонка может дать рваный кадр
  (старый type + новая label), но не висячий указатель. Не хранить в слоте
  pointer/динамическую строку без блокировки.

## Сборка (top-level)

- **`IDF_ACTIVATE` в Makefile указывает на скрипт активации Espressif Installation
  Manager (`eim`), не на стандартный `export.sh`** (`Makefile:3-5`) — `export.sh`
  ищет другое Python venv и падает в этой среде.
- **Автоопределение USB-порта приоритизирует VID Espressif (0x303A)**
  (`Makefile:52-76`) над CH340/CP210x/FTDI — чтобы не подхватить случайное
  USB-serial устройство на той же машине.
- **`dependencies.lock` пинит IDF `6.0.2` точно, манифест требует только `>=5.3`**
  (`dependencies.lock:88-91` vs `main/idf_component.yml:2`), а Makefile по
  умолчанию активирует именно `activate_idf_v6.0.2.sh` (`Makefile:5`). При апгрейде
  версии IDF нужно синхронно поправить все три места, иначе `make build` тихо
  использует не тот тулчейн.
- **Встроенный `lv_font_montserrat_20` содержит только `0x20-0x7F,0xB0,0x2022`
  (базовая латиница + градус + буллет), кириллицы нет** (сгенерировано с `-r`
  флагом в `managed_components/lvgl__lvgl/src/font/lv_font_montserrat_20.c:5`).
  Русский текст в `lv_label_set_text*()` отрисуется пустыми глифами. UI-тексты
  в `render.c` — намеренно на английском по этой причине, не стилистический
  выбор. Чтобы завести кириллицу, нужен отдельный шрифт/диапазон в menuconfig,
  что раздует бинарник (уже впритык, см. заметку про partition table ниже).
- **Шрифт LVGL по умолчанию — Montserrat 20px, помечен как TODO**
  (`sdkconfig.defaults`): "перенесено с 1.47" панели", нужно пересмотреть
  под 3.49" экран при переделке layout. Montserrat 14 включён отдельно для
  часов в углу главного экрана; без `CONFIG_LV_FONT_MONTSERRAT_14=y` в
  локальном `sdkconfig` (он gitignored) линкер не найдёт `lv_font_montserrat_14`
  — defaults сами по себе уже существующий sdkconfig не перепишут.
- **Partition table принудительно `SINGLE_APP_LARGE` (1.5MB)** (`sdkconfig.defaults:25-26`)
  именно из-за того, что более крупные шрифты не влезают в дефолтный 1MB —
  неочевидная связь с конфигом шрифта.

## client (Go)

- **На macOS голый Go-бинарник киллится сразу при обращении к Bluetooth**
  без `NSBluetoothAlwaysUsageDescription` (`client/README.md:13-16`) — бинарник
  обязан запускаться из `.app`-бандла с `Info.plist`, лежащим в репо. Запуск не
  через бандл = тихий краш/kill.
- **Первый запрос Bluetooth-разрешения должен идти из пользовательского
  Terminal, не через автоматизацию** (`client/README.md:20-23`) — иначе macOS
  привяжет разрешение не к тому процессу, и приложение упадёт. Легко попасться
  при скриптовании первого запуска.
- **Окно приёма нового бондинга — 60с после Pair на Settings, не от boot**
  (`client/README.md`, совпадает с прошивочной `BLE_APP_PAIRING_WINDOW_SEC`).
  Синхронизация между клиентом и прошивкой ручная, никакого runtime-согласования нет.
- **UUID периферии кэшируется на диск** (`/tmp/aiboard-client.ble-addr`,
  `client/internal/ble/client.go:22-27,322-353`) — обход известного бага
  CoreBluetooth: она может перестать ре-анонсировать известную периферию при
  `AllowDuplicates=false`. Без кэша переподключение к уже спаренной плате может
  тихо никогда не найтись через скан.
- **Ретраи при неудачном коннекте** (`client/internal/ble/client.go:198-201`) —
  обход бага в `tinygo.org/x/bluetooth` на macOS: неудачный коннект CoreBluetooth
  может вернуть zero-value `Device` вместо ошибки, что паникует при первом
  использовании; ловится через `recover()` (`client.go:278-283`) и трактуется
  как временная ошибка.
- **Только та горутина, что нашла устройство, может звать `StopScan`**
  (`client/internal/ble/client.go:248-250`) — иначе race со `StopScan` на
  небуферизованном scan channel библиотеки на macOS.
- **Не класть `#RRGGBB` в unquoted `JSON ?=` в Makefile.** `#` начинает
  комментарий Make, payload обрезается → `unexpected end of JSON input`.
  Дефолтный пример живёт в `client/examples/all_slots.json`; `make send`
  без `JSON=` читает файл. Чем грозит: вернуть цвета в `JSON ?=` в одну
  строку Makefile — снова пустой/битый JSON при `make send`.
- **`run` раскладывает Codex на слоты 1–4, без цвета экрана и LED.**
  (`client/codex.go`, `client/hook.go`) `slot_1` — gauge остатка квоты;
  `slot_2` — компактный остаток до сброса (`1d3h` / `15h` / `9h50m`) +
  подпись `to reset`: сутки всегда с часами, минуты только если меньше
  10 часов; латиница, в шрифте платы нет кириллицы; `slot_3` — gauge
  прогресса к сбросу (окно 7 суток → 0%, момент сброса → 100%);
  `slot_4` — имя хука текстом (CamelCase с `\n` между словами: слот
  160px, Montserrat 20 не держит `PermissionRequest` в одну строку),
  не свёртка в working/attention/stopped. `fg` по настроению события:

- **`Flush` всегда вклеивает `unix` + `tz_offset` с часов компьютера**
  (`client/internal/board/client.go` `stampComputerTime`: `time.Now().Unix()`
  и `time.Now().Zone()`). Слоты сравниваются отдельно: если они не изменились
  и предыдущая метка моложе минуты — BLE-запись пропускается, иначе часы на
  плате разъедутся с Mac. Не класть время в один из `slot_N`. Чем грозит:
  вернуть `DeepEqual` всего State включая unix — Flush каждую секунду;
  не слать `tz_offset` — плата покажет UTC, не ЧП компьютера.
