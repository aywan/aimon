# Правила для агентов

## Структура проекта

Прошивка ESP32-S3 (ESP-IDF, NimBLE, LVGL) для платы Waveshare ESP32-S3 Touch
LCD V2; BLE-имя `aw_extramon_1` + отдельный Go-клиент под macOS.

- `main/` — точка входа (`main.c`), верхнеуровневый `CMakeLists.txt`/`idf_component.yml`.
- `components/` — один ESP-IDF компонент на функциональную область платы:
    - `battery` — чтение ADC, оценка % заряда.
    - `ble` — NimBLE GAP/advertising/security (`ble.c`) + GATT-сервис (`gatt_svc.c`).
    - `events` — единая точка входа для пользовательских действий (`events_post()`).
    - `lcd` — драйвер панели, touch-контроллер, питание/reset через I/O-экспандер.
    - `power_button` — опрос кнопки питания, debounce, long-press → hard power-off.
    - `render` — LVGL UI, единственный подписчик на изменения `state`.
    - `rtc` — PCF85063 на системной I2C; стена часов компьютера через BLE `unix`/`tz_offset`.
    - `sd` — одноразовый mount TF-слота (FAT32) на boot для `bg.png`/`fg.png`.
    - `state` — общее состояние приложения; один callback на изменение (см. KB).
- `client/` — отдельное Go-приложение под macOS: BLE-клиент + `.app`-бандл
  (обязателен для доступа к Bluetooth на macOS) + `README.md` с протоколом.
- `docs/` — документация проекта, включая [KNOWLEDGE_BASE.md](docs/KNOWLEDGE_BASE.md).
- `build/`, `managed_components/` — генерируются тулчейном/менеджером компонентов,
  не редактировать руками и не описывать в базе знаний как "код проекта".
- `sdkconfig*`, `dependencies.lock`, `Makefile`, `CMakeLists.txt` — конфигурация
  сборки ESP-IDF; версия IDF пинится сразу в нескольких местах одновременно
  (см. раздел "Сборка" в KNOWLEDGE_BASE.md) — менять согласованно.

## Как вести проект

- **Перед тем как полагаться на схему платы/даташит — сверяйся с вендорским
  (Waveshare) примером кода.** Схема этой (V2) платы уже не раз расходилась с
  реальным подключением пинов (см. компонент `lcd` в KNOWLEDGE_BASE.md) —
  эмпирика и вендорский код надёжнее подписей на схеме.
- **Изменения, влияющие на аппаратное поведение, нельзя считать завершёнными
  без проверки на реальном железе.** Юнит-тестов/эмуляции для аппаратной части
  нет. Собери (`make build`), прошей нужной целью (`make app-flash` сохраняет
  BLE-бонды в NVS; `make flash`/`make erase-nvs` — когда нужно их сбросить) и
  попроси пользователя проверить поведение на плате, прежде чем закрывать задачу.
- **Если решение — эвристика или непроверенное предположение** (например, порог
  "батарея не подключена"), явно говори об этом пользователю, а не выдавай за
  проверенный факт — и фиксируй как такое в KNOWLEDGE_BASE.md.
- **Архитектурная договорённость:** единственная точка входа для пользовательских
  действий — `events_post()` (`components/events`); состояние живёт в
  `components/state`, у него один предполагаемый подписчик — `render`. Новый
  источник ввода не должен звать `state_set_*()` в обход `events`.
- **Если по итогам обсуждения решено что-то НЕ реализовывать** (например, отказ
  от индикации зарядки по тренду напряжения — слишком шумно и медленно для
  живого UI), зафиксируй причину отказа в KNOWLEDGE_BASE.md, а не только в
  переписке — иначе вопрос будет подниматься заново вслепую.

## База знаний нетривиальных решений

[docs/KNOWLEDGE_BASE.md](docs/KNOWLEDGE_BASE.md) — накопительная база нетривиальных
решений, обходов багов железа/библиотек и архитектурных договорённостей прошивки.

**Правило:** при работе над задачей, которая вводит новое нетривиальное требование,
спецификацию, обход бага или архитектурную договорённость (то, что нельзя вывести
простым чтением кода) — актуализируй `docs/KNOWLEDGE_BASE.md` в рамках той же
задачи, а не отдельным шагом позже:

- **Новое нетривиальное решение** — добавь запись в соответствующий раздел
  (что / почему / чем грозит + ссылка `файл:строка`), по формату, описанному в
  начале файла.
- **Уточнена/изменена спецификация или зафиксировано требование** (протокол,
  формат данных, поведенческий контракт, аппаратное ограничение) — зафиксируй её
  в базе знаний, а не только в коде или переписке с пользователем.
- **Решение устарело** (код изменился, обход бага больше не нужен) — поправь или
  удали соответствующую запись, не оставляй базу знаний в противоречии с кодом.

Не добавляй в базу знаний то, что и так очевидно из чтения кода — только скрытые
причины, ограничения и риски, ради которых база и существует.
